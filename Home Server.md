# Self-Hosted Home Server: CasaOS, Immich, and AdGuard Home

## Project Overview

This project documents the deployment and troubleshooting of a self-hosted home server using legacy hardware. The goal was to build a personal server capable of hosting a photo-management and backup service with Immich, alongside network-wide DNS filtering using AdGuard Home.

Rather than only documenting the final configuration, this project records deployment errors, root-cause analysis, configuration changes, and lessons learned during troubleshooting.

## Objectives

- Repurpose an old Acer laptop as a home server.
- Install Ubuntu Server LTS on a 500 GB HDD.
- Deploy CasaOS as a web-based server management interface.
- Deploy Immich for self-hosted photo and video management.
- Deploy AdGuard Home for DNS-based ad and tracker filtering.
- Troubleshoot Docker Compose configuration and network port conflicts.
- Document the process as a cybersecurity and systems-administration portfolio project.

## 2. Immich Deployment and Troubleshooting

### Objective

Deploy Immich as a self-hosted photo and video management service using a multi-container Docker Compose configuration.

The intended stack included:

- Immich server
- PostgreSQL database
- Redis-compatible cache/queue service, as required by the selected configuration
- Immich machine-learning service

The configuration was being deployed through CasaOS's custom application interface.

### Problem 1: Missing environment file

**Error observed**

```text
Failed to load /tmp/casaos-compose-app-.../env:
open /tmp/.../env: no such file or directory
```

The temporary path contained by the error was generated by CasaOS during the custom Compose deployment.

### Root-cause analysis

The deployment failed because CasaOS attempted to load an environment file from a temporary path that did not exist at the time of the operation.

The Compose configuration referenced an external environment file through `env_file:`. The error indicates a problem resolving or staging that file in the CasaOS deployment workflow.

This does not necessarily mean that Docker Compose itself cannot use environment files. Docker Compose supports `.env` files and `env_file`; the failure occurred in the specific deployment path being used.

### Troubleshooting approach

1. Inspected the custom Docker Compose configuration.
2. Identified the environment-file reference associated with the error.
3. Checked whether the expected environment file was present and correctly named.
4. Considered moving service-specific variables into inline `environment:` blocks.
5. Planned to redeploy and inspect the resulting container status and logs.

Example of inline environment configuration:

```yaml
services:
  example:
    image: example/image:latest
    environment:
      EXAMPLE_SETTING: "value"
```

This is a simplified illustration, not a complete Immich configuration.

### Technical lesson

A Compose deployment can fail before the application even starts if its configuration files or environment variables cannot be resolved. Troubleshooting therefore needs to distinguish between:

- Compose parsing or configuration errors
- Missing files and incorrect paths
- Container startup failures
- Application-level errors after startup

### Resolution status

The missing environment-file error was identified. The inline-environment approach was considered as a workaround. A successful redeployment should be confirmed with container status, application logs, and a browser-access test before marking this issue resolved.

Official Immich deployment documentation:

https://docs.immich.app/install/docker-compose/

## 3. AdGuard Home Deployment and Troubleshooting

### Objective

Deploy AdGuard Home as a DNS filtering service for the local network.

AdGuard Home can filter DNS requests to block many advertising, tracking, and known malicious domains. Network-wide use requires clients to send their DNS queries to the AdGuard Home server.

Official project: https://github.com/AdguardTeam/AdGuardHome

### Problem 2: Host port 53 conflict

**Error observed**

CasaOS displayed port-conflict warnings for host port 53, affecting both TCP and UDP.

Port 53 is the standard port used by DNS.

### Root-cause analysis

Ubuntu Server may run `systemd-resolved`, which provides local DNS resolution and commonly listens on `127.0.0.53:53`.

If another service or container attempts to bind to an overlapping host address and port, the bind operation can fail because the address is already in use.

The exact process and listening address should be confirmed on the server rather than assumed.

### Diagnostic commands

Check which process is listening on port 53:

```bash
sudo ss -lntup | grep ':53'
```

Check the resolver service:

```bash
systemctl status systemd-resolved
```

These commands help identify the process, protocol, and listening address responsible for the conflict.

### Workaround considered: Change the host port

A port mapping such as:

```yaml
ports:
  - "5353:53/tcp"
  - "5353:53/udp"
```

maps host port 5353 to container port 53.

However, this is **not a complete solution for ordinary network-wide DNS filtering**. Most clients configured through DHCP expect their DNS server to listen on port 53 and do not provide a standard way to specify an alternative DNS port.

This mapping may be useful for a limited test, but it should not be documented as a successful network-wide DNS configuration without evidence.

### Alternative: Resolve the host port conflict

AdGuard Home's official guidance explains how to configure `systemd-resolved` so that its local DNS stub no longer occupies the conflicting address and port.

The general troubleshooting process is:

1. Identify the process using port 53.
2. Review the current resolver configuration.
3. Back up relevant configuration files.
4. Follow the official AdGuard Home instructions for configuring `DNSStubListener` and `/etc/resolv.conf`, if appropriate for the system.
5. Restart the resolver service.
6. Recheck port 53 availability.
7. Configure AdGuard Home to listen on the intended host address and port.
8. Test DNS resolution before changing router-wide DNS settings.

Official troubleshooting reference:

https://github.com/AdguardTeam/AdGuardHome/wiki/FAQ

**Important:** Changing the resolver configuration incorrectly can break DNS resolution on the host. Do not disable or reconfigure `systemd-resolved` blindly.

### Verification

Before marking AdGuard Home operational, verify that:

- The container or service is running.
- DNS is listening on the intended host address on port 53 over TCP and UDP.
- DNS queries receive valid responses.
- The query log records requests.
- A test client can browse normally when using AdGuard Home as its DNS server.

### Resolution status

A port-mapping workaround and a host-resolver configuration change were considered. The final configuration should be documented as resolved only after the listening ports and DNS queries have been tested successfully.

## 4. Troubleshooting Methodology

The problems encountered demonstrate why reliable systems administration requires more than copying a deployment template.

The troubleshooting process used in this project was:

1. **Observe:** Record the exact error message rather than relying on a general description.
2. **Identify the layer:** Determine whether the failure is in configuration loading, container startup, host networking, or application behavior.
3. **Investigate:** Use service status, listening-port checks, configuration inspection, and container logs.
4. **Form a hypothesis:** Identify a likely root cause that matches the observed evidence.
5. **Apply a controlled change:** Change one relevant setting at a time and retain a way to revert it.
6. **Verify:** Confirm the service works from the perspective of an actual client.
7. **Document:** Record the error, cause, change, test result, and any remaining limitations.

## 5. Security Considerations

- Keep the CasaOS dashboard and service administration interfaces restricted to the trusted local network.
- Use strong, unique passwords for administrator accounts and databases.
- Do not publish secrets, database passwords, access tokens, or private environment files in the GitHub repository.
- Avoid exposing Immich, AdGuard Home, or the Docker administration interface directly to the public internet.
- Use persistent storage so service data survives container recreation.
- Maintain a separate backup of important photos and videos.
- Keep Ubuntu Server, Docker, CasaOS, and application images updated.
- Verify the source of installation scripts and container images before running them.

## Conclusion

This project explores how to repurpose legacy hardware into a self-hosted server and how to troubleshoot issues that arise when deploying services through a container-management interface.

The most important lessons are that configuration files must be resolved correctly before containers can start, host-level services can conflict with container port mappings, and a successful deployment must be verified through real service tests rather than assumed from a completed installation process.
